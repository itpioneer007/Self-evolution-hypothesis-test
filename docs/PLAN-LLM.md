# 接模型方案（待确认，未实施）

> 目标：把现在「模板 + 人工填写」的出题器，换成「按所选教材版本真出题、真判、真回灌」的三段流水线。
> 本文只是方案，不含实现。确认后再按第八节分批动手。

## 一、现在是什么，缺什么

| 环节 | 现状 | 接模型后要改什么 |
|---|---|---|
| 选版本 / 单元 | 顶栏只有一本教材的 6 个单元（人教 PEP 四上） | 版本下拉改成「版本 → 单元」两级；教材库加第二个文件 |
| 环节 1 规划 | 人工从 33 条候选知识点里挑，格子由 `generateCells()` 排 | 模型提考点意图，格子仍由代码盖 |
| 环节 2 生成 | 九字段全部人工填写 | 模型按一行计划出 JSON，代码逐项校验 |
| 环节 3 质检 | 人工勾 23 条 | 模型给条款号，代码闸有最终否决权 |
| 记忆库 / 下一轮 | 已占用角度自动排除，错题投影靠人工看 | 错题投影压成结构化 brief，直接进环节 1 的提示词 |
| 作答 / 变体 | 已跑通（判定、变体、写错题） | 不变。变体继续走确定性派生，不接模型 |

**必须先说清一件事**：现在「版本」只有一个选项。接模型不会凭空变出湘少版、新湘鲁版——要真按版本出题，得先把对应教材入库。数据结构已经留好（`SHT_BOOK.units` 是数组，`setUnit()` 换词表/句型/语音/情境域/白名单五样），加一本是数据活，不是架构改造。

## 二、三段各自的输入输出

三次调用都走 OpenAI 兼容的 chat/completions，`response_format: json_object`，输出必须能直接 `JSON.parse`。

### 调用 A · 规划（5 行计划）

输入：

```json
{
  "book": {"id": "PEP-G4A", "name": "人教PEP 四上", "grade": "四年级"},
  "unit": {"id": "U1", "title": "My classroom", "topicDomain": "学校"},
  "words": ["classroom", "window", "blackboard", "..."],
  "patterns": ["Where is it? — It's in / on / under ...", "..."],
  "phonics": [["cake", "cat"], ["date", "dad"]],
  "allowedFunctionWords": ["a", "the", "is", "..."],
  "brief": {
    "priority": [{"kp": "spelling · blackboard · oa + ar", "missCount": 2, "lastAt": "..."}],
    "blockedCells": [{"type": "听音选义", "scene": "学校", "level": "认", "distractor": "同类不同物"}],
    "levelHint": "本单元上一轮真会 0 个，整体降一档"
  },
  "count": 5
}
```

输出：

```json
{"plans": [
  {"kp": "phonics · a / a-e · cake 与 cat 长短音",
   "cause": "音近混淆", "ability": "phonics",
   "scene": "学校", "level": "辨",
   "whyThisOne": "上轮错在 a-e 读成短音，这次只考这一组",
   "nextIfWrong": "先做词形辨认，再回辨音"}
]}
```

**模型只填「考什么」，不填格子**。格子是 `{题型, 场景, 考查层次, 干扰项类型}` 四维，由 `generateCells()` 在占用表之外确定性分配，再回填进计划行。理由见第四节第 1 条。

### 调用 B · 生成（单题九字段）

一次一题，不批量。上下文只给这一行计划和本单元词表——不给整册，也不给其他题的题干（防模型把上一题的句式抄过来）。

输出：

```json
{"knowledgePoint": "phonics · a / a-e · cake 与 cat 长短音",
 "ability": "phonics",
 "prompt": "听录音，选出你听到的单词。",
 "audioText": "cake",
 "options": ["cat", "cake", "dad"],
 "answer": "cake",
 "analysis": "cake 里 a-e 读字母音，cat 是短音。",
 "nextIfWrong": "先做词形辨认，再回辨音"}
```

`cell` 不从模型取，用计划行里那一个。

### 调用 C · 质检（条款号）

输入是题的全部字段 + 该单元的完整词表 + 23 条文本。输出：

```json
{"verdict": "fail",
 "fails": [{"id": "C3", "reason": "选项 cat 与 dad 都读短音，干扰项不能区分长短音"}],
 "note": "改掉 dad，换一个长音词"}
```

### 代码闸（调用 B 之后、调用 C 之前必跑）

`validateQuestion(question, unit)` 纯函数，逐条返回 `{id, ok, detail}`：

| 编号 | 判什么 | 不过怎么办 |
|---|---|---|
| V1 | 题干、选项、解析里的每个英文词都在「本单元词表 ∪ 全册功能词」 | 判超纲，退回 |
| V2 | 答案严格等于某个选项（归一化后） | 退回 |
| V3 | 三个选项互不相同 | 退回 |
| V4 | 题干里不出现答案原词（拼写题最易犯） | 退回 |
| V5 | 解析 ≤ 25 字且不含「本题考查」这类空话 | 退回 |
| V6 | 听力题的 `audioText` 必须存在，且其答案与 `answer` 一致 | 退回 |
| V7 | `knowledgePoint` 与计划行一致，`cell` 与分配的一致 | 退回 |
| V8 | 与同轮其他题不同格（复用 `cellFingerprint`） | 退回 |

**V1 是这套东西的命门**。模型的默认行为是往「更地道」的方向写，一写就超纲。必须硬查，不能靠提示词自觉。

## 三、错题怎么回灌下一轮

现在的 `projectWeaknesses()` 已经能把错题按错因聚成投影，缺的是「压成一段能塞进提示词的 brief」。新增 `buildRoundBrief(unitId, round)`，输出就是第二节里 `brief` 那个形状：

```json
{
  "priority": [{"kp": "...", "missCount": 2, "stage": "variant-failed"}],
  "mastered": ["kp-U1-04"],
  "blockedCells": [...],
  "levelHint": "整体降一档 / 持平 / 升一档",
  "avoidScenes": ["家庭"]
}
```

规则：

- 近两轮内 `missCount ≥ 2` 或「变体也错」的考点，进 `priority`，最多 3 条。
- 两枪都对的考点进 `mastered`，下一轮**不再出**（除非别的考点全出过了）。
- 上一轮退回率最高的条款，转成生成时的禁忌句（例如 P3 挂了两次 → 提示词里写「连续两道不能同题型」）。
- 学生画像为空（第一轮）时不给 `priority`，只给 `blockedCells`。

这是「下一轮能根据错题记录判断怎么出」的落点，不额外引入新概念。

## 四、四个关键判断（这套方案能不能成立就看这四条）

1. **格子不给模型。** 让模型自己分配四维格子，5 道题会收敛到最省力的那一格（diversity collapse），而且没法验证它说的「不一样」是不是真的。格子是组合问题，代码算得又快又可复算，模型只负责「这一格考什么」。

2. **质检模型没有通过权。** 它只能说「挂」，不能定「过」。通过的最终依据是代码闸全绿 + 模型无否决。否则接上模型就是让生成方给自己判卷（self-confirming loop），出题质量会看起来变好、实际变松。

3. **词表必须硬查。** 模型不会知道「四年级上册没教过 curtain」，它觉得这词很自然。V1 逐个词查表，含全册功能词白名单，否则每题都会被判超纲——这两个方向都会翻车。

4. **变体不接模型。** 变体有四条硬规则（同格子、换答案、留旧答案当诱饵、换题面），确定性派生已经能覆盖七个题型。交给模型生成变体，就得再写一套 audit 去防它偷懒，收益为零。以后真要让模型出变体，也必须过同一个 `auditVariant()`。

## 五、模型接法与密钥

实测 `POST https://api.deepseek.com/chat/completions` 对 `Origin: null` 返回 `access-control-allow-origin: null`，**file:// 打开可以直接调**，零依赖静态页的前提不破。

两种落法：

| | 浏览器直连 | 加一层本地代理 |
|---|---|---|
| 改动 | 顶栏加一个「模型」设置项，key 存 localStorage | 加 `tools/llm-proxy.js`（Node 内置模块，约 40 行） |
| 优点 | 立刻能跑，不动架构 | key 不出本机进程，能记日志、能限流 |
| 缺点 | key 在浏览器里，页面被改就能被读走 | 多一个进程要起 |
| 适用 | 你自己在本机试 | 给别人用 / 以后上线 |

建议：先直连。key 只填在设置里，`localStorage` 单独一个 key，导出 JSON 时剔掉。**不要提交进仓库，不要发布成公网页面。**

## 六、成本与耗时

一轮 5 题：1 次规划 + 5 次生成 + 最多 5 次质检（退回重出另算），约 11–16 次调用。

- 单次生成按 3–5 秒估，一轮 40–70 秒。
- token 粗估：输入每题约 1.5k（词表 + 提示词），输出 300，一轮 2–3 万，成本在分级钱级别。
- 传输量最大的部分是词表。18 个词 + 6 个句型的 JSON 很小，不需要做检索。

## 七、失败怎么办

| 故障 | 处理 |
|---|---|
| 返回不是合法 JSON | 抓第一个 `{` 到最后一个 `}` 重试一次；再失败记「接不住」 |
| JSON 合法但代码闸不过 | 带条款号退回生成，最多重试 2 次；仍不过就标红，不塞进本轮 |
| 模型质检判「挂」但代码闸全绿 | 以模型为准（它可能发现了语言学问题），但必须写条款号；无条款号不采纳 |
| 网络 / 额度错误 | 停在当前步，保留已生成的题，不整轮重来 |
| 全程失败 | 退回现有的人工填写链路，功能不删 |

## 八、分批实施

| 批次 | 内容 | 产出如何验证 |
|---|---|---|
| P0 | 设置项（key / 模型 / 连通性测试）+ 单题生成打通 | 点一次生成，01 里出现一道可作答的题 |
| P1 | 整轮 5 题 + 代码闸 V1–V8 | 冒烟测试加「每道生成题必过 V1–V8」 |
| P2 | 规划环节接模型（格子仍代码盖） | 5 行计划的格子互不相同 |
| P3 | 质检模型 + 退回重试 | 故意造一道超纲题，看它被退回并写条款号 |
| P4 | 错题 brief 回灌环节 1，跑完两轮 | 第 2 轮的 priority 里出现第 1 轮错过的考点 |
| P5 | 第二本教材入库（版本下拉真的有两个） | 切版本后词表、句型、白名单同步换 |

P0–P1 就能回答「模型能不能出题」；P4 才能回答「自进化有没有发生」。后者需要真实学生做两轮，不是跑一次就有结论。

## 九、要你先定的四件事

1. **第二批入库哪本教材**：湘少版五上 / 新湘鲁版五上 / 暂时只用 PEP 四上。
2. **模型与 key**：是否用 DeepSeek（`deepseek-chat`），key 由你在设置里填。
3. **模型出的题能不能手改**：建议能改（模型出品当草稿，人保留最终编辑权）。
4. **生成失败时是否允许退回人工填写**：建议允许，不做成硬依赖。

## 十、这方案不能解决什么

- 5 题 2 轮的样本量不随接模型变大。模型让出题变快，不让「是否有效」的结论变强。
- 判对错仍是字符串比对，不是语法判定。
- 23 条里有一部分（F5 情绪安全、P5 位置合适）模型和代码都判不准，仍需人过一眼。
